# 命中@5 90% 是怎么算出来的：20 道题和一张判定表

先说清楚这个数的完整口径，免得被单独拎出去用：

> **命中@5 = 90%（18/20），是人工建的 20 题评测集上人工判的；0.13 秒是检索段的平均耗时，不含大模型生成。**

四个数字绑在一起才成立。少任何一个，剩下的就变成了一个好看的、但没法被追问的百分数。

## 一、症状：被问「检索准不准」，我答不上来

系统能跑通之后，我自己问了自己一句：检索到底准不准？

第一反应是"还行"——随手问几个问题，答案看着都对。但"看着都对"经不起第二次追问：准，是准在第一条就是对的文档，还是准在前五条里恰好有一条能答上？

更麻烦的是我没有分母。没有分母的准确率不是指标，是印象。所以先停下来，把"准"拆成可以数的东西。

## 二、"命中"必须先定义，否则测的是错觉

最省事的判法是：看 top1 返回的文档对不对。文档名一致就算命中。

这个判法会骗人。一份研报里"营业收入"出现十几次，向量召回的文档全对，但返回的那一段可能是"营业收入构成说明"，而不是"本期营业收入同比变化"所在的段落。文档级判命中，这一题算过；实际用起来，模型拿这段答不出用户要的那个数。

**"看起来对"和"能答上来"之间，差的是段落。** 所以判定拆成两层：

| 判法 | 看什么 | 会不会虚高 |
|---|---|---|
| 文档级 | top5 里有没有目标文档 | 会，同一文档内段落随便错都算过 |
| 文档 + 段落级 | top5 里有没有一条既来自目标文档、内容又落在目标段落 | 不容易，但标注更费时间 |

我用的是第二种。代价是每题标注时间大概翻倍，收益是这个数敢被追问"你怎么判的"。

## 三、20 道题怎么挑的

素材是 10 份财报和研报，20 个问题全部手写，覆盖几类典型问法：单点事实（某个财务数字）、需要跨段拼接的（原因和结果分在两处）、表格里的数、以及带年份限定的问法。

每题标两列：**目标文档**、**目标段落**。目标段落用原文里的一句话做锚点，判定时看返回内容有没有覆盖这句。

为什么不用随机抽样？因为随机抽出来的是"文档里随机位置的一句话"，它的分布跟真实提问几乎不重合。真实提问集中在少数几类句式上，随机抽样等于用更简单的问题集去测一个更难的系统。20 题这个量级，随机反而更没代表性。

代价也要写明：**这 20 题是我自己挑的，不是随机抽的。** 它能说明方向，不能说明泛化。

## 四、计时必须贴着代码写

0.13 秒这个数，单看毫无意义——它可以是向量检索的时间，也可以是整条链路的时间。我把它钉在具体的函数上。

检索主方法 `retrieve()` 在 `backend/app/rag/retriever.py`，链路是两阶段：

```python
def retrieve(self, query: str, top_k: int = 10,
             sec_code: Optional[str] = None) -> List[Dict]:
    # 第一阶段：粗排
    vector_results = self._vector_search(query, top_k=top_k * 2, sec_code=sec_code)
    bm25_results = self._bm25_search(query, top_k=top_k * 2)
    merged = self._rrf_merge(vector_results, bm25_results, k=60)

    # 第二阶段：精排
    if self.use_rerank and len(merged) > 0:
        merged = self._rerank(query, merged)

    results = merged[:top_k]
    return results
```

0.13 秒计的就是"进这个函数到 return"这一段：嵌入、向量与 BM25 双路召回各取 `top_k * 2`、RRF 融合（k=60）、cross-encoder 精排、截 top_k。**不含后面的大模型生成。**

两个数字因此不能混：检索 0.13 秒；本地 1.5B 模型流式出答案，首字 1–3 秒，整段看长度。要是有人问"用户等多久"，答案是后者，不是 0.13。

顺带说清 0.13 秒为什么能这么低——不是因为用了 HNSW（那是必备项，不是亮点），而是三件事：召回只取 2×top_k，不是全库；精排只对十几条候选做，不是对全库；嵌入和精排服务常驻本地，没有冷启动。

## 五、结果，以及我不敢补的那两块

| 指标 | 数值 | 口径 |
|---|---|---|
| 命中@5 | 18/20 = 90% | 人工判，文档 + 段落双条件 |
| 平均检索耗时 | 0.13s | 检索段，含精排，不含生成 |

20 题里错的两题，我事后没有做归因归档——当时只记了"过 / 不过"两栏，没记"为什么不过"。这是这份评测的第二个短板，比样本量小更难受：**没有失败归因的评测，下一轮改完还是不知道有没有改对。**

所以严格讲，它不是回归测试。回归测试要能重复跑、能对比修复前后；这份东西是我手工跑了一遍、记在表格里的一次人工验证，没落成可执行的文件。

## 六、可以搬走的一条

指标不是数字，是"数字 + 判定标准 + 样本 + 计时边界"四件套。少一件，这个数在被人追问的第一次就会碎。

具体动作很小：**在评测表里加两列——`judged_by` 和 `judge_criteria`。** 谁判的、按什么判的，跟分数写在同一行。

下次再有人问"90% 怎么算的"，我可以直接把那行表格推过去，不用靠回忆把口径重新拼一遍。
