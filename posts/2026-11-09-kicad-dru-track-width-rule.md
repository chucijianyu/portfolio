# 昨天 0/0，今天 25 条 error：设计规则不落盘就等于没通过

## 现象：同一块板，两次 DRC 两个结果

昨天定稿的那块 X 形四臂一体板，跑出来是 0 违规 / 0 未连接。今天把 `xframe_routed.kicad_pcb` 单独拷到另一个目录重跑一遍，变成 25 条 error，全是 `track_width`。

板子一个焊盘都没动，布线一条都没变。变的只是「目录里还有没有那个规则文件」。

## 定位：25 条不是 25 个错误，是 25 段线

违规原文长这样：

```
走线宽度 (电路板配置约束 最小宽度 0.2000 mm; 实际 0.1500 mm)
```

括号里那句就是判据：**最小宽度 0.2000 mm 来自「电路板配置」**，而实际走线是 0.1500 mm。所以这不是布线错了，是「拿哪把尺子量」的问题。

数一下板上的线：`(segment` 一共 461 段，其中 436 段 0.2mm、25 段 0.15mm。25 条违规正好等于 25 段 0.15mm 的线，一条不多一条不少——DRC 数的是**线段数**，不是网络数。

这 25 段全在 F.Cu，按网络分：

| 网络 | 段数 |
|---|---|
| GND | 7 |
| OSC_IN | 4 |
| OSC_OUT / LSE_IN / LSE_OUT / 3V3 / MOTOR1 / MOTOR2 / SWDIO | 各 2 |

看网络名就知道它们在哪：8MHz 主晶振、32.768kHz 副晶振、SWD 调试口、MOTOR 输出——全是从 LQFP-48 的 STM32F103 和 QFN-24 的 MPU6050 底下往外逃的短线。这些区域 0.2mm 挤不进去，只能 0.15mm。0.15/0.15mm 属嘉立创、华秋的常规制程，不是冒险。

那 0.2 是哪来的？这个目录里**没有 `.kicad_pro`**。KiCad 的板级约束存在工程文件里，没有工程文件就没有这份设定，CLI 回落到内置默认 0.2mm。

## 修法：把规则写成文本，跟板子放一起

`xframe_routed.kicad_dru` 全文就三行：

```
(version 1)
(rule "min track 0.15mm (fab capability, JLCPCB/HQPCB standard)"
	(constraint track_width (min 0.15mm)))
```

规则文件必须与 pcb **同目录、同 basename** 才生效。

## 为什么是改尺子，不是改线

有个更省事的做法：把那 25 段线直接拉到 0.2mm，DRC 一样变绿，还不用多带一个文件。我没这么做，原因有两个。

一是这些线本来就窄得有理。它们夹在 48 脚和 24 脚封装的引脚之间，是从引脚底下钻出来的逃逸段，不是随便画的。加宽到 0.2mm 就得重新过间距检查，绿色可能只是从线宽挪到了间距上。

二是「改板子」和「改尺子」必须能分清。改线是设计决策，要有人认账；改规则是工艺声明，得有板厂制程兜底。0.15mm 对应的是嘉立创、华秋的常规能力，这条规则写下来等于把「我按 0.15 设计」这句话留在了仓库里。要是把线拉宽了却不说，下一个人看到的是一块"本来就 0.2"的板，前面为什么这么布就再也读不出来了。

所以这里选的是把尺子写下来，并且写明白它从哪来——规则名里那句 `fab capability, JLCPCB/HQPCB standard` 不是装饰。

## 今天新踩到的两个坑，都实测过

**坑一：改名就静默失效。** 我把 dru 改名成 `board_dru.kicad_dru` 再跑，25 条原样回来。没有警告，没有"规则文件未找到"的提示，什么都没有。

**坑二：默认退出码不管违规。** 想让它进 CI 的话，这句是不够的：

```bash
kicad-cli pcb drc --format json -o drc.json xframe_routed.kicad_pcb
# 25 条 error，退出码 0
```

得加 `--exit-code-violations`：

```bash
kicad-cli pcb drc --exit-code-violations --format json -o drc.json xframe_routed.kicad_pcb
# 25 条 -> 退出码 5；0 条 -> 退出码 0
```

两个坑叠起来的结果很反直觉：**一块有 25 条 error 的板子，在最常见的那条命令行下，是"通过"的。**

## 结果

| 条件 | 违规 | 未连接 |
|---|---|---|
| 无 dru（KiCad 默认 0.2） | 25 | 0 |
| dru 改名（basename 不匹配） | 25 | 0 |
| 同名同目录 | 0 | 0 |

未连接数三种情况下都是 0，它跟线宽判据无关，不受影响。这也反过来说明 25 条纯粹是规则的事，板子本身没退化。

边界也说清楚：这个 dru 里只声明了 `track_width`，clearance 还是默认值；`x_drc7.json` 还带着 5 项 `ignored_checks`（缺 courtyard、过孔未居中、封装 filter 不匹配等），而且因为没有原理图工程，`schematic_parity` 是空的。所以这 0/0 的准确说法是「在只约束最小线宽的规则集下，几何与工艺层面 0 违规」，不等于电气全对。

## 可搬走的一句

最早那次 0 违规，是在 pcbnew 的设置里把最小线宽（`m_TrackMinWidth`）改到 0.15 跑出来的。报告很漂亮，规则没落盘。换台机器、换个目录、交给别人复跑，那个 0 就还原不出来。

一个通过如果 checkout 不出来，它就不是通过，只是一次截图。

所以规则要写成能进 git 的文本，检查要带能失败的退出码。这两件事都不难，难的是记得——报告变绿的时候，人一般不会想去问"凭什么绿"。
