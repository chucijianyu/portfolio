# 本地账本说没发过，远端说已经在了：幂等判断该信谁

## 现象

每天 12:30 有个任务往仓库发一篇文章。这类任务的重跑场景比想象中多：手动补跑一次、机器重启后 cron 重放、上一次跑到一半挂了再起一遍。三种情况都要求同一个结果——同一天不能出现两篇一样的文章，也不能多一个提交。

我最初的想法很自然：本地记一个"今天发过了"的标记，跑之前查一下。这个做法的问题不在实现，在判断依据。本地标记和远端仓库是两个状态，它们会分叉：标记写了但推送失败、推送成功但标记没落盘、标记文件被误删。只要分叉，判断就会错，而错的方向恰好是最坏的那个——重复发布。

## 我怎么定位

我没有去加更多本地状态，而是反过来问：这次发布到底改了远端什么，我能不能直接问它。

脚本里每篇稿子落成的路径是固定的：

```python
target = f"{POSTS_DIR}/{post['date']}-{post['slug']}.md"
```

`date` 和 `slug` 都来自稿件的 front matter，不是运行日期。这一点很关键——10-30 那次补发，稿子写的是 `date: 2026-10-27`，落成的就是 `posts/2026-10-27-*.md`，不会因为跑得晚就变成 10-30 的文章。路径因此成了这篇文章的稳定身份，跟"哪一天跑"无关。

既然路径稳定，那么"发过没有"这个问题，远端仓库自己就能回答。

## 修法

判断只有一处，一次 GET，写在**任何写操作之前**：

```python
tok = token()

# --- 幂等 ---
exists = api("GET", f"{API}/contents/{target}?ref={BRANCH}", tok, allow_404=True)
if exists and not a.force:
    print(f"[SKIP] {target} 已存在（sha {exists['sha'][:10]}），本次不重复提交")
    ledger_add(post, target, None, skipped=True)
    if src.startswith(QUEUE):
        _archive(src)
    sys.exit(0)
```

三个细节决定了它为什么够用。

**一是问远端。** `ref=BRANCH` 指定查 main 分支上的这个路径，`allow_404=True` 让"不存在"返回 `None` 而不是抛异常。判断不依赖任何本地文件，本地账本删了也不影响结论。

**二是位置在写之前。** 这段代码排在所有 blob、tree、commit 之前。跳过分支里没有任何写操作，所以重跑一次不会在对象库里留下孤儿对象，更不会产生第二个提交。

**三是跳过时也要收尾。** 命中 SKIP 之后仍然调 `_archive(src)`，把稿件从 `content/queue/` 挪到 `content/published/`。这一步是为崩溃场景准备的：如果上一次推送成功、归档之前进程死了，稿件还躺在队列里，下一次跑就会走 SKIP 分支顺手归档。队列靠归档清空，不靠账本。

## 结果与一处真实的代价

现在 `content/published/` 里 12 篇，脚本的退出码是三档：0 成功或已跳过、2 队列空、1 出错。这三档让外层循环能自己决定下一步——拿到 2 就去写新稿，拿到 0 什么都不用做。

代价是账本会记错。看那条跳过分支：`ledger_add(post, target, None, skipped=True)`，sha 传的是 `None`。如果真实情况是"推送成功但归档前挂了"，那么下次跑会记成 `skipped=True, sha=None`，而这篇其实是我自己推上去的。账本说"跳过"，仓库说"早就有了"。

我没有去修这个。要修就得在跳过时再查一次提交历史、把 sha 反查回来，代价是多一次请求和一段推理，换来的是账本更准确——但账本本来就不参与任何判断，它只是个审计日志。这里的选择是：**判断只信远端，账本允许不准**。反过来做（信账本、远端当备份）在第一次分叉时就会重复发布。

`--force` 那条路还有两处配套，否则覆盖会留下脏数据。索引行按 `(date, slug)` 去重，重发不会在 `posts/README.md` 里留两行：

```python
rows = [r for r in rows if not (r["date"] == post["date"] and r["slug"] == post["slug"])]
rows.append({"date": post["date"], "title": post["title"],
             "slug": post["slug"], "tags": post["tags"]})
```

归档撞名时加时间戳后缀，不会把旧的已发布稿覆盖掉：

```python
if os.path.exists(dst):
    dst = dst.replace(".md", f"-{datetime.now().strftime('%H%M%S')}.md")
```

## 幂等的边界到此为止

认清这条路保证的是什么，比实现它更重要。幂等键就是路径，路径只由 `date` 和 `slug` 组成。于是：

改标题，路径不变，`--force` 会更新正文和索引里的标题；改 `date` 或 `slug`，路径就变了，脚本会认为这是一篇**新文章**，原样再发一遍，旧的那篇永远留在远端。它保证的是"同一个键不重复",不是"内容永远最新"。想纠正一篇已发布的稿子，得用 `--force` 且别动 date 和 slug；一旦动了，就得自己去远端删旧文件——脚本不会替你删。

这个边界不算缺陷，是幂等本身的定义域。所有靠"键相同就跳过"的系统都这样：键换了就是新东西。

**可搬走的一句：幂等判断要问远端真实状态，并且必须发生在第一次写之前。** 顺序错了，判断再准也没用——写已经发生了，跳不跳都晚了。
