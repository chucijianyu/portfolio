# 引用点不回原文：一次 RAG 页码管道的排查记录

先说结论，免得被数字带偏：

> **23% 不是溯源准确率，是分块里"页码字段的填充率"。** 它只回答一件事——引用能不能定位到第几页；它不回答检索准不准。

这两件事经常被说成一个数。下面这件事的过程，基本就是被这个混淆坑进去、又爬出来的过程。

## 一、症状：一个"看起来还行"的百分比

系统上线后有个统计页面，其中一行是"引用可溯源率"。1430 个分块里，357 个带页码，算下来 24.97%。

四分之一。看着像"待优化"，不像"坏了"。所以它在那儿躺了很久。

真正让我起疑的不是这个数字，而是另外一个：**357 全部来自表格块，文本块一个都没有。**

严格地说，不是"文本块很少"，是"文本块恒等于 0"。一批数据里两种块的占比碰巧相等，可能是巧合；两个独立批次都精确相等，就不是巧合了。

我又在本机留存的 10 篇原件上重跑了一遍：981 块，226 带页码，23.0%。而这 10 篇里表格块正好 227 个——差的 1 个是个 docx 表格，没有 page 字段。

**同一批数据、两个口径、同一个现象。** 到这里可以确认：这是代码路径的结构性问题，不是数据脏。

## 二、第一反应是错的：用正则抓页号

页信息其实是有的。解析阶段拼全文时，每页开头都会埋一个标记：

```python
# document_parser.py 里干的活（示意）
full_text += f"[第{page_no}页]\n" + page_text
```

所以我第一版修法非常直接：拿到块文本，正则找 `\[第(\d+)页\]`，第一个命中就是这块的页码。

跑完，抽 47 个块回 PDF 原页比对，准确率 **63.8%**。

不到三分之二。比不修好，但一个"定位"字段只有 63.8% 可信，等于没有。

## 三、错在两个地方，而且第一个错在我自己

拆开看，63.8% 背后是两个问题叠在一起。

**第一个：我的测量方法先错了。** 抽查脚本取块开头 40 个字去 PDF 里搜。可这个分块器有 64 个字符的 overlap——块开头那 64 字本来就属于上一页。也就是说，我拿"上一页的尾巴"去验证"本页的页码"，测的本身是个错的东西。

**第二个：块内的页标记不只一个，位置不同含义不同。**

有个块，`[第3页]` 出现在第 267 个字符的位置。前 267 字还在第 2 页，后面才是第 3 页。取第一个标记，就把整块判成第 3 页——错了一半。

反过来，如果块里压根没有标记呢？那说明它是上一块的续块，页码应当继承，而不是归零。

## 四、正确的判定：看标记在块里的位置，不是看有没有标记

修法是把"取第一个"换成"按位置分三种情况"：

```python
PAGE_MARK = re.compile(r'\[第(\d+)页\]')

def _resolve_pages(self, text_chunks):
    spans = []
    current = 0
    for tc in text_chunks:
        marks = self.PAGE_MARK.findall(tc)
        if marks:
            start, end = int(marks[0]), int(marks[-1])
            current = end
        else:
            start = end = current
        spans.append((start, end))
    return spans
```

对照关系写清楚：

| 标记在块里的位置 | 含义 | 判定 |
|---|---|---|
| 贴块开头（overlap 之后立即出现） | 本块从这一页开始 | 该页 |
| 出现在块中部 | 前半段承自上一页 | 跨页块，记 `(start_page, end_page)` |
| 块内没有标记 | 上一块的续块 | 继承上一块末页 |

注意这里有个细节值得单独说：**overlap 会把上一页的标记带进来**。所以"贴开头"不能理解成"第 0 个字符"，要理解成"overlap 长度之后第一次出现"。这个坑不写清楚，下一个改这段代码的人一定踩。

## 五、结果，以及剩下 11% 为什么不硬凑

同一批材料，981 块不变：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 分块数 | 981 | 981 |
| 带页码 | 226 | 874 |
| 覆盖率 | 23.0% | **89.1%** |
| PDF 类文档 | 0% | **100%** |

按位置判定重跑，47 个块 **47/47 全中**。

剩下的 10.9%（106 块）全部来自两个 `.docx` 文件。docx 是流式文档，没有物理页，`python-docx` 读不到分页，解析时也不埋页标记。

能不能凑到 100%？能——估算一个"每页多少字"再除一下。但那是在数据库里写假信息，比缺字段更糟。正确的做法是换定位维度：docx 记段落区间（`para 12–18`），PDF 记页码。**两个维度各管各的，不硬凑成一个好看的数。**

## 六、怎么证明没把别的东西改坏

只证明"字段被填上了"是不够的，必须证明"别的东西没动"。

办法是拿新旧两版分块器在同一批 10 篇原件上逐块 diff：**981 块内容完全一致**，分块边界、块类型、块序号零变化，唯一变化的是页码字段（648 个从 0 变成正数）。

另外把备份版留在仓库里，`citation_coverage.py baseline` 会自动加载它，一条命令就能在同一批数据上跑出修复前的 23.0%。对比不是靠记忆里的数字，是靠现在还能跑出来的数字。

## 七、可以搬走的一条

这个 bug 一开始没人发现，不是因为它隐蔽，是因为**埋标记的代码和读标记的代码之间，没有任何东西检查"标记到底有没有被读走"**。

解析那边认认真真写 `[第3页]`，分块那边压根没传 `page_number`。两段代码各自都"对"，拼起来数据是空的。

所以后来我加了个校验：统计"文本里有页标记、但页码字段为 0"的块数。这个数只要非零，就是 bug。

**这类缺陷不该靠人眼发现，该靠指标兜住。** 一个恒等于"表格块占比"的百分比，本来就是最明显的告警信号——只是它长得太像一个正常的、待优化的数字了。
